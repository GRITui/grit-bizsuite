## Current state

`apps/grit-pos` and `apps/grit-inventory` maintain entirely separate `Product`/`Variant` tables in separate Postgres databases with independent `cuid()` id spaces (`apps/grit-pos/prisma/schema.prisma:200-259`, `apps/grit-inventory/prisma/schema.prisma:173-240`). The only cross-referencing column is `Variant.inventoryVariantId` on the POS side (`apps/grit-pos/prisma/schema.prisma:235-242`), a nullable id backfilled by the inbound `catalog.variant_synced` webhook (`apps/grit-pos/app/api/events/grit/route.ts:104-119` handler, `:161-183` implementation) whenever Inventory creates or renames a variant (`apps/grit-inventory/src/app/api/variants/[id]/route.ts:110,147`, `apps/grit-inventory/src/app/api/products/[id]/variants/route.ts:69`, emitted via `publishCatalogVariantSynced`, `apps/grit-inventory/src/lib/events.ts:215-222`). Critically, the sync only *links* — it never creates a POS-side `Variant`; POS's own catalog is explicitly documented as authoritative for which variants exist locally (doc comment, `apps/grit-pos/app/api/events/grit/route.ts:38-44`), and a `sku` with no local match is a silent no-op. `transaction.completed` items carry both `sku` and, once linked, `inventory_variant_id` (`packages/shared-events/src/contracts.ts` `TransactionCompletedData`), and Inventory's webhook handler tries the id first, SKU-string second (`apps/grit-inventory/src/app/api/events/grit/route.ts:159-163`), logging an `UnmatchedSaleItem` row on a full miss (`schema.prisma:895-914`) rather than silently dropping it as before. BACKLOG.md's "POS ↔ Inventory SKU alignment" section documents this precisely and explicitly flagged the ownership question as unresolved (BACKLOG.md:347-352) — that question is now resolved: Inventory owns the catalog.

## Target state — recommendation

**Recommendation: cached read-only mirror on POS, extended `catalog.variant_synced` carrying full product/variant data — not a live-read design.** Three pieces of evidence rule out "POS queries Inventory live at checkout":

1. **POS is offline-first by explicit design, not just aspiration.** `PromotionRule`'s doc comment states outright: "grit-pos is offline-first and never calls another app live at checkout time" (`apps/grit-pos/prisma/schema.prisma:380-384`), and `lib/promotions.ts` repeats it (`:8-9`). There's a real hand-rolled IndexedDB offline queue (`apps/grit-pos/components/pos/offlineQueue.ts`) with a dedicated sync endpoint (`app/api/orders/offline-sync/route.ts`) for ops captured with no network at all. A design where ringing up an item requires a live call to grit-inventory would regress this guarantee for every sale, not just an edge case — a register with a flaky connection currently degrades gracefully; live-catalog-read would make it degrade to "can't sell."
2. **The precedent already exists and already works this way.** `promotion.updated` is the existing analogous cross-app catalog-adjacent sync: Inventory owns pricing rules, pushes the full rule payload to POS, POS caches it locally (`PromotionRule` model) and evaluates entirely offline (`apps/grit-pos/prisma/schema.prisma:389-438`). `catalog.variant_synced` is explicitly framed as being in that same lineage (its doc comment cites the `promotion.updated` precedent directly, `packages/shared-events/src/contracts.ts` `CatalogVariantSyncedData` docstring). Extending the *same event* to carry the full product/variant record, instead of introducing a new live-query surface, is continuity, not reinvention.
3. **POS's current checkout path is already "local-DB read, not truly live cross-app read."** `GET /api/catalog` (`apps/grit-pos/app/api/catalog/route.ts`) reads from POS's own DB; add-line reads `Product`/`Variant` from POS's own DB and snapshots `unitPrice`/`lineTotal` onto `OrderLine` at that moment (`apps/grit-pos/app/api/orders/[orderId]/lines/route.ts:47-83`), but the *catalog data itself* (name, sku, vatApplicable, inventoryVariantId) is **not** denormalized onto `OrderLine` — it's live-joined off `Product`/`Variant` at every subsequent read via `orderInclude` (`apps/grit-pos/app/api/orders/_lib/queries.ts:25-40`). So POS already depends on having a local, always-available copy of catalog rows to join against; the only question this design needs to answer is *who writes those rows*. Making Inventory the writer (via sync) rather than POS's own create/edit flow is a much smaller change than eliminating local rows outright.

**Hybrid element:** stock-sensitive operations (does this SKU have available quantity right now, at this store) should **not** be part of the mirror. POS has never modeled stock at all — there's no `quantityOnHand` anywhere in `apps/grit-pos/prisma/schema.prisma`. Keep it that way: POS continues to sell optimistically off the mirrored catalog (price, name, VAT flag, active/inactive) and let Inventory's existing `transaction.completed` consumption path (`apps/grit-inventory/src/app/api/events/grit/route.ts:98-`) be the sole place stock is decremented, exactly as today. Do not add a live "check stock before selling" call — that reintroduces the offline dependency this design is trying to avoid, for a check that FIFO/backorder handling downstream can already absorb. If real-time stock-aware selling is wanted later, that's a distinct, separately-scoped feature (e.g. an async low-stock banner fed by `inventory.threshold_breached`, which already exists), not part of this cutover.

**Tradeoff being accepted:** a genuine mirror means eventual consistency — a price change in Inventory takes one webhook round-trip to reach POS, same latency profile `promotion.updated` already has today, which is an accepted, working pattern in this codebase. The alternative (live read) would trade that small staleness window for a hard availability dependency that conflicts with an explicit architectural invariant. Given the codebase already accepts eventual consistency for pricing/promotions, extending the same tolerance to product/variant identity is consistent, not a new risk class.

## Migration path

- **New canonical products (Inventory-authored going forward).** Any product a tenant creates from now on is created in Inventory; POS receives it via the extended sync event and creates a local mirror row keyed by `inventoryVariantId`/`inventoryProductId` (see below), never a POS-native `cuid()`.
- **Existing POS-only rows (today's baseline: any `Variant` with `tenantId`/`sku` null — "legacy hospitality variants have neither tenantId nor sku," per the schema doc comment at `apps/grit-pos/prisma/schema.prisma:230-231` — and any matrix retail variant that was never synced because no `catalog.variant_synced` event was ever emitted for it, e.g. seeded directly into POS's DB rather than created via Inventory's `/api/products/:id/variants` route).** These need a one-time backfill pass: for each tenant, walk POS's local `Product`/`Variant` rows that have no `inventoryVariantId`, and for each one either (a) match it to an existing Inventory `Variant` by `(tenantId, sku)` where `sku` is non-null and a match exists, populating the link retroactively, or (b) push it *into* Inventory as a newly-created canonical product/variant (a reverse, one-time sync, the opposite direction from the steady-state flow) where no match exists and the item is a real stock-tracked good, or (c) leave it as a POS-local-only "quick item" (see below) where it was never meant to have an Inventory equivalent at all.
- **The "coffee problem."** A made-to-order espresso has no discrete inventory unit, no FIFO cost, no reorder threshold — forcing it into Inventory as a stock-tracked `Variant` (which defaults `quantityOnHand: 0`, `reorderThreshold: 0`, `unitCost` optional, per `apps/grit-inventory/src/app/api/products/[id]/variants/route.ts:8-16`) is workable numerically (threshold 0, never breaches) but conceptually wrong — Inventory's whole domain model (`StoreStock`, `StockLot`, FIFO consumption, `VariantLocation` planogram slots, `PickTask`/`PackTask`) assumes something with a physical shelf location and countable quantity. **Recommendation: Inventory needs a lightweight "not stock-tracked" product type** — a boolean or type flag on `Product`/`Variant` (e.g. `Variant.stockTracked: Boolean @default(true)`) that suppresses `StoreStock`/`StockLot`/reorder-threshold UI and skips stock decrement on `transaction.completed` consumption for that item, while still making it the canonical catalog record POS mirrors. This is cheaper than maintaining two parallel "is this canonical" concepts (an Inventory-owned catalog plus a POS-local escape hatch), and matches how AGENTS.md already frames hospitality as "optional plugin traits" on an otherwise channel-agnostic core — non-stock-tracked is exactly such a trait, and it belongs on the canonical record, not as a fork of catalog ownership. A POS-local-only escape hatch is worth keeping only as a narrow last resort (see open questions) — every non-stock-tracked item still benefits from single-app catalog editing (name/price changes in one place), which a POS-side-only record would defeat.
- **What happens to sales during the gap.** Until backfill completes, keep today's tolerant behavior: unmatched-by-id-or-SKU items still get silently skip-but-persisted-to-`UnmatchedSaleItem`, exactly as approach 3 already ships (`apps/grit-inventory/src/app/api/events/grit/route.ts:169-187`). This is not new risk — it's the same graceful-degradation path already in production; the SSOT cutover should not regress it to a hard failure.

## API/event contract changes needed

- **Extend `CatalogVariantSyncedData`** (`packages/shared-events/src/contracts.ts`) from an id/sku/name link into a full mirror payload: add `product_id`, `product_name` (already present), `category_name` (or `item_group`/`item_sub_group` names — POS's `Category` model is flat, one level, `apps/grit-pos/prisma/schema.prisma:187-198`, vs. Inventory's two-level `ItemGroup`/`ItemSubGroup`, `:594-628` — this mismatch needs a decision, see open questions), `price` (maps to POS's `basePrice`/variant `priceDelta` split — Inventory has a single flat `price` per variant with no base/delta split, `apps/grit-inventory/src/app/api/products/[id]/variants/route.ts:8-11` schema, so POS's product/variant price-delta modeling either needs to collapse to Inventory's flat-per-variant-price model or Inventory needs to start carrying a delta concept — recommend collapsing POS to flat price per mirrored variant, since `priceDelta` was POS's own invention for a UI concept Inventory doesn't share), `vat_applicable` (moves ownership of this flag to Inventory — see "what breaks" below), `attributes` (matrix axes, already JSON on both sides), `is_active`, `stock_tracked` (new field, see above), and `deleted`.
- **New event or reused event for product-level (not variant-level) changes.** Today's event is per-variant; a product-level rename/deactivate with no variant change would need either a dedicated `catalog.product_synced` event or folding product fields into every variant event (simplest — keep one event type, redundantly carrying product fields per variant, matching how `promotion.updated` already denormalizes its whole payload per event rather than normalizing across events).
- **New "full resync" endpoint on Inventory,** e.g. `GET /api/catalog/export?tenant_id=` or reuse of a bulk variant list, so a newly-onboarded POS tenant (or one recovering from an outbox gap) can seed its mirror from scratch rather than waiting for every historical `catalog.variant_synced` event to replay. The existing outbox (`EventOutbox` model, both apps) supports replay of undelivered events but not a "give me full current state" pull — that's a genuinely new surface, not an extension.
- **Deprecated fields:** POS's `Variant.priceDelta` (folds into Inventory's flat price, see above) and POS's `Product.basePrice`/`Variant.priceDelta` split generally becomes a derived display concern at most, not a stored independent value once Inventory is the source; `Variant.vatApplicable` stops being POS-editable (no UI edits it today anyway — confirmed no admin catalog UI exists in POS at all, see below) and instead is purely sync-received.
- **`Variant.inventoryVariantId`** stops being an optional backfilled link and becomes the mirror's actual foreign identity — i.e., POS's local `Variant.id` for a mirrored row *is* (or is keyed 1:1 with) `inventoryVariantId`, removing the current "local id ≠ synced id, joined by a nullable column" indirection for anything created after cutover.

## What breaks / needs care

- **Promotions are actually SKU-keyed today, not POS-local-id-keyed — correcting the stated assumption.** `PromotionRule.items` and `lib/promotions.ts`'s cart matching (`apps/grit-pos/lib/promotions.ts:30-34, 129-133`) work entirely off `sku` strings pulled from `PromotionUpdatedData.items`, whose contract doc explicitly says "always resolved to SKUs, not internal variant ids — SKU is the only join key POS and Inventory share" (`packages/shared-events/src/contracts.ts`). This is *good news* for the SSOT cutover: once Inventory is the source of truth and SKUs stop drifting (a single canonical `Variant.sku` per mirrored row), promotion matching gets strictly more reliable for free, with no `PromotionRule`/`promotion.updated` contract change required. The one thing that *does* need care: if a future iteration wants promotions to match by `inventoryVariantId` instead of `sku` (more robust to a SKU rename), that's an additional, optional hardening pass, not a blocking dependency of this cutover.
- **`Variant.vatApplicable` ownership.** Today it's a plain POS-local column with no sync in either direction and no admin UI to edit it (see below — POS has no catalog admin UI at all), so in practice it's stuck at its schema default (`true`) for every variant that wasn't hand-seeded otherwise. Recommend: Inventory becomes the owner (add `vatApplicable`/`vat_applicable` as a real Inventory `Variant` column, since VAT-exempt-goods status is a catalog-master-data fact, not a POS-checkout fact), pushed down via the extended sync event; POS's column becomes purely a synced mirror, matching every other catalog field's new treatment.
- **OrderLine snapshot semantics — must be protected, and today's code has a real gap to close, not just preserve.** `unitPrice`/`lineTotal` are correctly snapshotted at add-line time (`apps/grit-pos/app/api/orders/[orderId]/lines/route.ts:69-83`) and explicitly documented as such ("snapshotted so historical reporting is unaffected by later catalog price changes," `apps/grit-pos/prisma/schema.prisma:317-318`). But `product.name`/`variant.name`/`variant.sku` are **not** snapshotted — they're live-joined at every read via `orderInclude` (`apps/grit-pos/app/api/orders/_lib/queries.ts:25-40`). Today this is low-risk because POS's own `Product`/`Variant` rows are essentially immutable after creation (no edit UI exists). Once Inventory can rename/re-describe a mirrored product and that change flows down via sync, a *historical* order's displayed line item name could silently change to reflect today's catalog, which is exactly the failure mode `unitPrice` was deliberately protected against. **This needs closing as part of the cutover, not left as pre-existing debt**: either denormalize `productName`/`variantName`/`sku` onto `OrderLine` at line-creation time (consistent with the `unitPrice` precedent), or explicitly accept live-name-drift as intentional (unlikely, given the existing precedent argues the other way) — this is a real decision point, not a side effect to note in passing.
- **The variant matrix builder (`apps/grit-pos/lib/variantMatrix.ts`) is largely fine as-is** — it's a pure, isomorphic (client+server) function library over `{id, sku, attributes}` shapes with no direct Prisma dependency (confirmed: no `prisma.` calls in the file, no server-only import). It doesn't need to change *if* mirrored variants keep the same `attributes` JSON shape and `sku` field. What does need care: today `buildChildSku`/`expandChildSkus` are POS-side generation of a *new* SKU for a matrix combination — post-cutover, Inventory should own SKU generation for any matrix product (since it owns catalog identity), and POS's copy of this logic becomes read-only display/lookup (`resolveVariantSelection`), not a creation path. If POS's matrix UI currently lets staff create matrix variants locally, that capability needs to move to Inventory (see "no admin UI" note below — currently it doesn't exist as a live-write path in POS regardless).
- **No admin catalog management UI exists in POS today** — a repo-wide search of `apps/grit-pos/app` (excluding generated Prisma code) turns up zero product/variant create-or-edit routes or pages; the only catalog-facing route is the read-only `GET /api/catalog` (`apps/grit-pos/app/api/catalog/route.ts`), used by the register's `ProductPicker`. This substantially *de-risks* Phase 3 below (deprecating POS's create/edit UI) — there is nothing to deprecate. It does mean, though, that POS's current `Product`/`Variant` rows were populated by a seed script or direct DB write outside any documented app flow, which is exactly the backfill problem described above.
- **The public storefront/pickup and QR dine-in routes** (`app/api/pickup/[tenantSlug]/checkout/route.ts`, `app/api/public/table/[tableToken]/order/route.ts`) re-validate submitted cart lines against POS's local `Product`/`Variant` tables server-side (never trusting client-supplied prices, per the pickup route's own doc comment). These keep working unchanged under the mirror design since they're reading the same local tables — they just become reads of mirrored-not-native data.

## Phasing / rollout plan

This is too large for one PR. Proposed phases, each roughly a single builder-agent-sized slice:

1. **Phase 1 — extend the event, not the behavior.** Widen `CatalogVariantSyncedData` (contracts.ts) to carry the full product/variant payload described above; update Inventory's three emit sites (`variants/[id]/route.ts:110,147`, `products/[id]/variants/route.ts:69`) to populate the new fields; update POS's webhook handler (`app/api/events/grit/route.ts`) to upsert the new fields onto the existing `Variant`/`Product` row it already matches by SKU — but *keep* today's "no local match = no-op" behavior unchanged for this phase. Zero behavior change for end users; purely wire-format + handler-body work. Add the mirrored `stockTracked`/`vatApplicable` columns to POS's schema in this phase too (additive migration).
2. **Phase 2 — mirror-first creation.** Change the handler so a `catalog.variant_synced`/product-sync event with no local match now *creates* the POS-side `Product`/`Variant` row (instead of no-op), keyed so `inventoryVariantId` is the join key from creation, not backfilled later. Add the full-resync pull endpoint on Inventory + a one-time "hydrate my mirror" job/route on POS for already-provisioned tenants. This is the phase where POS "goes thin" for new catalog data going forward.
3. **Phase 3 — backfill + reconcile existing POS-only data.** Run the reconciliation pass described in "Migration path" per tenant: match-by-SKU where possible, push-to-Inventory-as-new for genuine stock-tracked orphans, flag/convert made-to-order items to Inventory's new `stockTracked: false` type. This phase needs the "not stock-tracked" product type shipped in Inventory first (own small slice, since it also needs FIFO/`StoreStock` consumption code paths to skip it — `apps/grit-inventory/src/lib/inventory.ts`'s `applyStockMovement` and the event-handler's stock-decrement loop both need a guard).
4. **Phase 4 — close the OrderLine snapshot gap.** Denormalize `productName`/`variantName`/`sku` onto `OrderLine` at creation time (or explicitly decide not to, see above) so historical orders are provably immune to later mirror updates — do this *before* Phase 2 goes live broadly, since Phase 2 is exactly what introduces catalog-driven renames flowing into POS for the first time. (Ordering note: this phase should probably run concurrently with or just before Phase 2, not strictly after — listed last only because it's independent of the mirror mechanics themselves.)
5. **Phase 5 — cutover + promotion/VAT ownership handoff.** Move `Variant.vatApplicable` to Inventory-owned + synced (small, additive on both schemas). Confirm promotion matching continues to work now that SKUs can't drift (should be a no-op verification pass, not new code, given promotions are already SKU-keyed). Turn on stricter handling of sync misses if desired (e.g. stop tolerating "no match" once backfill is confirmed complete for a tenant) — this is a policy flag change, not new mechanism.

Each phase above is disjoint enough to hand to separate builder-tier agents per the AGENTS.md 3-layer convention: Phase 1/2 touch `packages/shared-events` + both apps' event-handler files (architect-layer, since `packages/shared-events` is a cross-cutting shared package); Phase 3's reconciliation script and Phase 4's OrderLine migration are each a disjoint directory slice suitable for a mid-tier builder; Phase 5's small schema/UI-flag work is mechanical-sweep-sized.

## Open questions that need a human product decision

- **Should POS staff retain any ability to create a genuinely non-Inventory item at all** (a truly ephemeral, never-reported, never-priced-centrally special request), or should even made-to-order hospitality items always be canonical Inventory records with `stockTracked: false`? The document above recommends the latter for consistency, but it's a real product-experience tradeoff (an extra round trip/dependency on Inventory being reachable to add a new menu item) that a builder shouldn't decide unilaterally.
- **Category model mismatch:** POS's flat single-level `Category` vs. Inventory's two-level `ItemGroup`/`ItemSubGroup` — does the mirror collapse to Inventory's sub-group as POS's "category," dropping the group level entirely, or does POS's UI need to grow a second level? This is a UI/data-modeling decision, not an engineering one.
- **Downtime tolerance for the one-time backfill migration.** Is a maintenance window acceptable per tenant, or must the match/push-to-Inventory reconciliation run live against a serving system? This changes whether Phase 3 can be a straightforward batch script or needs to be an online, resumable, idempotent job.
- **Is silent-skip-to-`UnmatchedSaleItem` still acceptable *after* the cutover is fully rolled out**, or should a post-backfill sale with no catalog match become a hard error (since "no match" should no longer be a normal occurrence once Inventory is universally authoritative)? This is a severity/UX call, not something inferable from the code.
- **Who is authorized to still directly edit POS-local price/VAT fields during the transition window** (Phases 1-4, while both a legacy local value and a soon-to-be-synced value coexist) — is there a freeze on local catalog edits during migration, or does the sync event need "last writer wins" conflict handling for the overlap period?
